# Sky-Myce overhaul — implementation and verification, October 10, 2026

The follow-up **2.4.28** tracker repair is now deployed and installed. It restores historical totals and saved-report access and repairs new recording gaps; see the [tracker repair](dungeon-tracker-cutover.md) and [production deployment record](backend-deployment.md). The measurements and earlier deployment IDs below describe 2.4.27.

Release **2.4.27** targets **Minecraft 26.1.2 / Java 25**. It was uploaded to private R2, selected on `sky-myce-backend --env backend`, and installed through the authenticated loader in the user's existing Prism session. Menu, chest observation, legacy cutover and canonical chat changes are implemented and the full mod build/check passed. The persistent User Bot Gateway is deployed on the existing Cessna Cloudflare relay. A real Minecraft → Discord → Minecraft test now passes, including reply context and mention presentation. Party delivery remains explicitly unavailable because no backend-verifiable Hypixel party membership authority exists. A fresh live Hypixel reward chest remains unverified.

## Root causes and resulting behavior

**Performance:** catalog search reconstructed/tokenized entry metadata and sorted it on every query; settled navigation repeatedly rebuilt the same six rectangles; Quick Settings allocated an unchanged comparison list each tick. The catalog now indexes immutable metadata/order once, navigation retains geometry until its layout inputs change, and Quick Settings compares at most eight original values directly. Heavy ambient motion stops at a settled pose. Existing authentication, feature updates, debugging and configurable visuals remain. Earlier feature-work/dependency reductions already existed in the starting tree and are not attributed to this release.

**Menu:** hover followed the previous painted lift/scale, so a stationary pointer near the lower edge repeatedly changed ownership as the card moved. Logical interaction bounds now follow category-to-rail layout rather than hover animation. Painted feature-card child controls still receive correctly inverted coordinates; clipping, unrevealed input and adjacent ownership checks remain. Dungeons, Combat, Economy, Cosmetics, Utils and Settings remain the six top-level destinations. Settings uses the shared compact rail instead of a separate wide sidebar. Clear category previews, selected icons/tooltips, separate Search/Quick Settings actions, contextual headings and direct control links reduce duplicate navigation. Favorites/Recent retain bounded identities. Light, Medium and Heavy keep distinct lift/depth/glow; the first introduction waits for shell arrival and saved introduction state prevents replay.

**Tracker:** the actual saved Handle log uses `RNG DROP! ... just found ...`, while the old parser accepted only `RARE REWARD! ... in their ... Chest!`. Source inspection also found short-title-only chest recognition, `customName`-only controls and unnormalized lore. Unknown costs prevented observations, a single matching inventory item could confirm every preview reward, repeated clicks replaced the baseline, and disabling Daily Digest prevented the shared inventory observer from feeding the tracker. These are repaired at their shared boundaries. The exact failed live GUI title/control/cost lore is absent from the log, so the compatibility aliases are source-supported fixtures, not a captured current Hypixel GUI.

Chest titles/controls use explicit bounded aliases and display-name/format normalization. Clicks must originate in the observed screen/container; reward IDs/counts refresh at the click. Unknown cost/market value stays unknown. A stable preview observation UUID binds account/profile/world/run and inventory baseline. Confirmation requires the matching server reward header and every expected physical inventory increase; essence-only receipts require that header too. Repeated events enrich one acquisition. Rerolls require exactly one observed Kismet decrease. Pending state uses monotonic expiry, bounded close grace and context resets; existing coalescing is reused. No old Handle acquisition was invented retroactively.

Old aggregate consumers also contaminated new run counts/timing/XP. The version 2 cutover preserves old rows with explicit legacy provenance, freezes historical net profit by floor, and starts separate confirmed run/receipt samples. Existing aggregate profit already contains old chest activity, so old receipts are not added to it again. Lifetime estimated profit displays inherited and new contributions; missing new prices/costs leave the combined estimate unknown rather than zero. The widget, overview, loot/timeline, XP/timing and party statistics use the intended generation. Corrupt/future archives or failed cutovers pause recording; exact originals and existing backups remain intact.

**IRC/backend:** commands exposed competing global/legacy concepts and the persistent Gateway had never been hosted. `/sm irc` now explicitly enables receiving and selects persistent global input; `/sm irc <message>` sends once without changing the mode. `/sm pc` selects a locked separate party mode and the message form reports unavailable; `/sm chat` restores normal input. Canonical help/settings and compatible global aliases agree. Failed sends, reconnects, stale receipts and timeouts never route selected-channel text into normal chat. The exact exit remains available before protected command dispatch if authorization expires; all account/send gates remain.

The account Worker rejects explicit party/unknown scopes before global/legacy dispatch. The installed Party API's client-observed UUID/role roster has no signed origin, stable party ID, revision or expiry that this backend can verify. Account authentication proves identity and installation authorization, not party membership. No client-selected room, forged roster, old `friends` room or Discord fallback grants party delivery. [The unresolved authority contract](party-chat.md) describes the exact requirement; this is not a completed private-party transport.

The new Cloudflare `GlobalChatGateway` uses the existing User Bot application/token/channel and existing authenticated global bridge. It retains one configured coordinator, resumable Discord session/sequence, shared alarms, bounded temporary packets and durable delivery receipts. Stable Discord nonces and receipt-before-ack prevent retry echoes. Guild/channel/application/author/scope checks, Message Content intent, terminal credential failures, full Discord cooldown deadlines, reconnect backoff and slow-handshake cancellation are covered. Admin/account HTTP interactions remain on their existing signed handlers.

The first real receive test exposed an additional replay ordering defect: the Gateway advanced its saved sequence while discarding missed dispatches before `RESUMED`. [Discord's documented resume order](https://docs.discord.com/developers/events/gateway#resuming) delivers these messages before the final event. The repair accepts them only during a Resume initiated for the previously validated bot/session and current socket, through unchanged filtering and atomic queue/sequence writes. Identify traffic before READY still cannot establish message delivery. The specific first user's drop is consistent with this defect, but its raw dispatch timing was not retained and cannot be proven retrospectively.

The next human message, `hello247`, was also verified in Discord and absent from native Minecraft chat. Short production health probes showed repeated transport disconnects. A localhost workerd network probe confirmed a second cause: [the runtime attaches an Upgrade request's abort signal to its returned WebSocket](https://github.com/cloudflare/workerd/blob/main/src/workerd/api/http.c%2B%2B#L1531). The ten-second handshake timeout therefore closed healthy sockets after connection. Upgrade attempts now use clearable controller timers, canceled on response headers; stalled handshakes still time out and bridge cancellation/generation, READY and heartbeat guards remain. The regression observes both adopted sockets beyond ten seconds and its negative control fails with the old timer behavior. This fix is deployed as Gateway version `ecd1963b-5bfa-4f2b-b981-be2703d5aeb1`.

A backend workerd fixture separately reproduced a lost subscription: an older cosmetics request resumed after its authority check and serialized its stale full-session attachment over a newer global opt-in. The client had a successful subscription receipt and therefore did not resubscribe. Handlers now refresh current attachments after authorization, commit subscription changes only for the latest per-scope server intent and recheck opt-in after awaited fan-out authorization. Temporary request tokens use a per-socket WeakMap, adding no persisted attachment fields or schema migration. Existing identity/lease, revocation and rate checks remain; no global concurrency lock is added. Real workerd tests cover both authorization waits, reused IDs, newer opt-outs, independent scopes, current feature credits/inboxes/watches, the attachment size limit and actual hibernation. Full relay tests, TypeScript validation and independent review passed. The backend-only fix is deployed as version `dd0588b1-a721-4695-9b62-ead63185c157`; mod and manifest remain 2.4.27.

## Measurements and limits

Comparable headless measurements ran before production menu edits and after them on the same Windows machine with Temurin **25.0.3+9**, existing Gradle JavaExec fixtures and no concurrent Gradle build. Timing is aggregate elapsed time divided by operation count; allocation is current-thread `ThreadMXBean`, including fixed fixture overhead. JIT/desktop timing variation remains.

| Warm operation | Before | Final full-suite run | Allocated before → after |
| --- | ---: | ---: | ---: |
| Six settled navigation rectangles per frame; 2,000 warm / 10,000 measured | 0.397 µs | 0.139 µs | 490 → 56 B/frame |
| Real catalog search; 145 entries, six queries, 360 warm / 600 measured | 547.155 µs | 81.091 µs | 1,316,888 → 6,576 B/query |
| Idle rasterizer, four graphics qualities | 0 dirty pixels/frame | 0 dirty pixels/frame | Unchanged 968–1,687 B/frame |

Search allocation fell about **99.5% in this fixture**. Intermediate search timings varied from 75.214 to 121.845 µs/query; this is not a game FPS claim. Active raster/page-blend timings were mixed, including slower samples, so no uniform renderer speedup is claimed. [The detailed menu report](menu-optimization-2026-10.md) includes query/layout/renderer conditions and all profile results.

Native JFR also recorded **245 seconds before and 245 seconds after** in the same Prism private world, actual Java 25.0.1, Minecraft 26.1.2, 210 loaded mods and 3840×2160 display. Before/after had 5,952/7,992 execution samples and 29,365/39,368 allocation samples. Array filling, frame limiting, third-party HUD queries, Minecraft chunk data and menu rendering all appeared. The recordings included different menu activity, JIT/desktop work and elapsed world/weather state: sample counts are not exact allocation totals, and neither FPS nor equivalent post-GC heap improvement is established. JVM arguments/properties/environment, process-start and exception-text events were excluded and checked. Redacted summary: `build/release-2.4.27-native-jfr-summary.json`; private recordings remain in the authorized visualization directory.

The prior installed 2.4.26 artifact was 13,991,254 bytes; 2.4.27 is **14,027,050 bytes**, an increase of 35,796 bytes (~0.26%). Existing compact dependency packaging was retained and verified; no new size reduction is claimed. The old broader performance report describes earlier work, not an additional saving from this release. Startup latency, controlled process CPU/RAM/FPS, low-end hardware and hour-scale soak comparisons remain unmeasured.
