# Personal RNG journal and observation reliability

The RNG journal queries the existing permanent `acquisitions.json` archive. It does not require Discord or a relay connection. Filters are saved separately in `rng_journal_view.json`; changing filters never edits acquisitions. The normal current-profile view contains confirmed supported personal acquisitions. All local profiles and explicitly labeled legacy reports remain available offline, without treating legacy reports as new measurements.

## Source-confirmed failures repaired

The pinned SkyBlock API 4.2.19 inventory event carries the container's GUI slot index and its backing `Slot`. GUI indexes change between the player's inventory menu and a chest menu. The rare-item removal watch previously stored one index scheme and compared it to the other; that could miss a removal, retain an old aggregate baseline and mask a later real increase. It now compares `Slot.getContainerSlot()` consistently. Direct player-inventory packets still use the existing coalesced observer because they bypass the slot event.

RNG inventory observation previously depended on Daily Digest readiness. Disabling Digest or encountering Catacombs profile-tab loading gaps could leave it unseeded even when the acquisition repository had an already verified matching context. RNG observation now seeds independently, preserves verified matching contexts through allowed dungeon tab gaps, and resets for actual profile, world or disconnect changes. A cold inventory seeds only a baseline; pre-existing rare items cannot become new drops. Daily Digest uses the same verified repository context rather than requiring the profile widget to be reloaded inside a dungeon.

A complete tracker receipt can arrive after a partial physical inventory delivery, or without the older rare announcement form. Completed receipts now notify the existing RNG presentation path. Both observers derive their permanent acquisition ID from the same first physical observation/item confirmation. A late complete receipt enriches the existing acquisition with run, chest, cost and value rather than creating a second personal or public event. Same-profile identity enrichment is accepted; a different Minecraft account cannot overwrite an acquisition. Personal server messages retain strict player/location/catalog matching, with bounded Minecraft formatting and space normalization. Party quotations and multiline inputs remain rejected.

A malformed community history entry previously caused the entire subscription parse to fail. Bounded valid siblings now survive, duplicate IDs collapse, and an empty successful response displays an explicit live-empty state. Malformed or oversized envelopes remain rejected. Privacy removal tombstones block delayed reports from returning, and received community events never enter the permanent personal journal or publication path.

## Honest views and compact HUD

Journal week/month/custom boundaries use UTC; weeks start on Monday and the selected custom end date is inclusive. Search, profile scope, activity, floor, ordering and legacy controls operate on immutable archive snapshots off the render thread. Each screen worker retains one running request and only the latest pending selection; generation and owner checks discard obsolete results. The history displays actual timestamps, quantities, source/context and known recorded estimates. New priced receipts retain the local evaluation timestamp separately from the drop timestamp; market cache age and historical missing valuation times remain unknown. Nullable fields remain backward compatible and are never backfilled into old records.

New item observations retain the actual plain display name and the pinned API's lore-derived rarity, including a recombobulated tier when present. Chest metadata is captured before reward ItemStacks are reduced to receipt data; Slayer metadata comes from the newly increased inventory item, not a previously held item. Conflicting same-ID stack metadata remains unknown. Late announcements may enrich an already confirmed matching acquisition but cannot create a second event. No lore, NBT or whole inventory is persisted for this presentation.

Trends compare all-time, current UTC week and current UTC month under the same local scope/search/activity/floor filters. They count confirmed observed item quantities, supported item and recorded rarity distributions, with an explicit Unknown rarity bucket. The day chart shows at most the latest 30 observed UTC days, explicitly omitting days with no observations. The latest twenty linked run groups compare observed quantities, known values, missing-price coverage, recorded duration and fully priced estimated chest profit including rerolls. Missing run context, timing, cost or value remains unknown; saved future observations are retained but excluded from current statistics. Legacy reports do not enter graphs, and counts do not claim game drop probability.

The optional community comparison uses `/community/journal-comparison` and the same consent-filtered `rng_drops` dataset as the leaderboard. Compatible all-time/week/month selections show acquisition-report counts for the current Minecraft identity across all its profiles and observed servers, accepted own shared counts and the mean across contributing identities. One acquisition report counts once even if its item quantity is greater than one; this differs explicitly from personal quantity graphs. Alternate Minecraft accounts, legacy records and future observations are excluded from the local comparison. Search, activity, floor, custom-date and legacy filters explain their incompatibility instead of comparing unequal selections. Global/RNG/leaderboard opt-out makes the own shared count unavailable. The server returns no participant names or IDs, and these self-reported consenting samples are not server-wide rates. Current profile and main/alpha server distinctions are absent from the shared schema, so no profile-only or main-server-only community statistic is claimed.

The optional Recent Personal RNG widget reads up to three confirmed current-profile archive events and caches by archive revision/context. It uses the existing shared HUD panel and has an explicitly labeled editor example. No network access, leaderboard recomputation or invented live values occur during rendering. Per-widget visibility/position/scale belong to the existing HUD editor. The tracker HUD and client info use the same panel vocabulary; the tracker preserves inherited/confirmed separation in a more compact layout. A failed widget render now rebuilds after a bounded retry and cannot prevent subsequent widgets from rendering; one warning covers a continuous failure streak.

The pinned owo adapter has a concrete failure-lifetime gap: it enables scissor before drawing, but a thrown draw skips the matching disable; its final cleanup resets adapter flags only. Its default graphics wrapper also shares Minecraft's matrix and clipping stacks. HUD extraction now uses an owo wrapper with independent stacks while submitting into the same Minecraft GUI render state. It copies the parent's pose and already transformed current clip, and retains the existing tooltip handoff. A failed component therefore cannot leave its matrix/scissor state on the next widget or vanilla layer. This repairs a source-confirmed error path; it is not evidence that the historical Ubuntu report had that cause.

The gameplay HUD is independently registered through Fabric's supported `HudElementRegistry` extraction callback before chat. The editor intentionally has additional example/retained content, while gameplay still respects F1, player existence, each widget's real context and visibility. The dungeon tracker intentionally hides during an unfinished active run; skill XP and ability notifications expire. The source audit found no confirmed KDE/Linux-specific rendering cause. [Fabric's HUD API documentation](https://docs.fabricmc.net/develop/rendering/hud) describes the callback, and the locally pinned 26.1.2 API remains the compatibility reference.

## Verification boundaries

The offline checks cover current personal announcement forms/formatting, cold inventory baselines, mixed partial/complete physical rewards, permanent cross-observer IDs beyond short chat deduplication, same-profile enrichment, cross-account rejection, archive restart/pins/legacy totals, observed item metadata, linked run comparisons, UTC boundaries, future exclusion, filter persistence, actual quantity distributions, unknown valuation coverage and canonical Digest deduplication. Community checks cover acquisition-report versus quantity units, account separation, UTC response integrity, consent removal, session changes, empty samples and malformed payloads against the production routes. Feed checks include valid/malformed siblings, empty responses and oversized envelopes. Existing tracker/chest fixtures retain context, run, expiry, GUI-close, reroll and unknown-cost safeguards. These fixtures use synthetic data; they do not open game chests or publish reports.

A fresh live Hypixel reward receipt and the reported Ubuntu 26/KDE gameplay failure still require environment verification. Windows fullscreen checks are performed by the main task after the build; editor visibility alone is not evidence of gameplay or Linux reliability. Historical repair notes in `dungeon-tracker-cutover.md` were used as context, not as proof of the current live state. No saved old acquisition is reconstructed or replayed into public leaderboards.
